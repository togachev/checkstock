# CheckStock — Где сейчас товар?

Прототип системы учёта остатков на складах фулфилмента (ФФ) с поддержкой FBS и FBO.
Выполнен в рамках тестового задания.

**Стек:** Python, FastAPI, PostgreSQL, SQLAlchemy, Jinja2 (Bootstrap 5).
**Запуск:** Docker Compose.

---

## Инструкция по запуску

Требуется установленный Docker и Docker Compose.
В корневой папке проекта выполните:

```bash
docker-compose up --build
```

Приложение будет доступно по адресу: **http://localhost:8000**

_Примечание:_ База данных PostgreSQL инициализируется автоматически при первом запуске. Тестовые данные (склады «Север» и «Юг», товары SKU-101, 102, 103) загружаются автоматически.

## Ключевые архитектурные решения

Здесь описано, как система решает неочевидные задачи из ТЗ.

### 1. Доступный остаток и товары «В пути»

- **Доступно** = `Физический остаток` – `Резерв FBS`.
- Товар, который находится в пути (между ФФ, в FBO или в FBS), не уменьшает доступный остаток на складе-отправителе (он уже списан), но и не прибавляется к остаткам получателя до момента нажатия кнопки «Принять». Он отображается в отдельном реестре «В пути».

### 2. Защита от двойного списания (Идемпотентность)

Реализована на двух уровнях:

- **Фронтенд:** Все кнопки форм (Принять, В путь, Резерв) блокируются через JavaScript после первого клика (`setTimeout(() => this.disabled = true, 10)`), что предотвращает случайный дабл-клик пользователем.
- **Бэкенд:** Каждая операция имеет статус (`IN_TRANSIT` -> `COMPLETED`). Повторный вызов эндпоинта `/receive` проверяет статус операции в БД: если он уже `COMPLETED`, транзакция не проводится повторно.

### 3. Удаление склада (Soft Delete)

По требованию ТЗ, при удалении склада остатки и история не должны теряться.

- Вместо физического удаления строки из БД, мы ставим флаг `is_deleted=True` (мягкое удаление).
- Склад исчезает из выпадающих списков в формах (приход, перемещение), чтобы по нему нельзя было провести новые операции.
- Однако в таблице остатков и в истории операций склад продолжает отображаться (с бейджем «Удалён»), чтобы менеджер видел, где физически находится товар.

### 4. Обработка нехватки на выбранном ФФ

При создании перемещения или отправки FBS/FBO система проверяет наличие именно на складе-отправителе. Если на выбранном складе не хватает товара, возвращается ошибка `400 Bad Request` с указанием доступного количества, даже если на других складах этот товар есть в избытке.

### 5. Использование ИИ при разработке

ИИ (DeepSeek) использовался для ускорения рутинных задач:

- Генерация HTML-шаблонов Jinja2 и CSS-классов Bootstrap.
- Написание базовых моделей SQLAlchemy.
- _Бизнес-логика_ (проверка остатков, обработка статусов, транзакции, защита от дублей) проектировалась и проверялась вручную.

## Структура проекта

- `app/main.py` — FastAPI приложение (роуты и бизнес-логика).
- `app/models.py` — Модели SQLAlchemy (Таблицы: Warehouse, Product, Stock, Operation).
- `app/database.py` — Подключение к БД.
- `app/templates/index.html` — Единый интерфейс (SPA-подобный экран).
- `docker-compose.yml` — Конфигурация для поднятия Web-сервера и PostgreSQL.
